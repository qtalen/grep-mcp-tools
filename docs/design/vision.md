# 愿景

## 北极星

一句话：**把 MCP 工具发现从"预加载"变成"按需 grep 检索"，治 agent 的上下文爆炸。**

背景痛点：企业内部 MCP 服务动辄上百个工具，agent 一挂载，20k~60k token 的工具定义常驻上下文，挤占任务空间、推高成本。本产品是一个代理层 MCP 服务：对下游只暴露三个工具（`search_mcp_tool` / `invoke_this_tool` / `check_mcp_status`），上游全部工具定义在启动握手时落成明文 JSONL 索引（一行一工具），agent 按需用关键词检索、按 target 透传调用。

价值账：常驻上下文从 20k~60k token（经验值）降到约 650 token（三个工具定义 + 动态注入的服务清单）；单次搜索按需消耗通常 ≤6k token（典型工具定义密度、30 条上限内）——真实数字由 B04 指标表实测输出（含直挂臂常驻实测与搜索响应体积）。

## 用户画像

- **主要客户**：企业内部 agent 应用的开发者/维护者。首个落地场景：公司内部基于 LangChain DeepAgents 的应用，经 langchain-mcp-adapters 以 stdio 方式挂载本代理。
- **最终受益者**：该应用的终端用户——agent 上下文不再被工具定义挤爆，任务质量更好、调用成本更低。

## 成功画面（怎么算做成）

三条可度量标准，由 agent 测试台的 A/B 实验量化（见批次 B04）：

1. **任务成功率**：代理模式 vs 直挂全部上游，差距 ≤10 个百分点。
2. **上下文节省**：常驻工具定义体积 ≥80% 缩减。
3. **零提示自主发现率**：纯自然语言任务（提示中零工具暗示）中，agent 无提示发起首次 `search_mcp_tool` 的比例 ≥80%。刻意用 deepseek-flash（reasoning_effort=low）这类弱推理模型做测试公民——笨乘客能看懂的路标，强模型必然更稳。

## 最难场景（产品赌的是什么）

下游 agent 的三层失败梯子（本文与台账多处引用）：

- **L0**：根本不知道背后还有外部能力——永远不发起任何调用，自校正回路无从启动（最致命）；
- **L1**：看到了这几个工具，但任务当前没想到该先用它们；
- **L2**：想搜了，但不知道该搜什么词（词汇失配）。

对应缓解：L0/L1 → description 动态注入（D-13）；L2 → 自校正回路（D-03/D-04/D-15）。

**agent 猜不出工具作者的词汇**：工具描述写 "audit trail retention"，agent 搜 "log history"，三次空手而归后带残缺信息干活。整个产品骑在关键词检索上，这是关键假设。缓解手段：自校正回路（零命中给服务名路标、超量给收窄提示）+ description 动态注入服务清单。若 B04 实验证伪此假设，需重新评估产品方向。为此放弃的替代方案：语义/向量检索（实测效果不好，见决策台账 D-11）。

## Non-Goals（不做什么）

| 不做 | 理由 |
|---|---|
| 语义/向量检索 | 实测效果不好（用户经验证据，D-11） |
| 提示注入防护 | 上游描述经搜索结果流入下游的风险，与直挂上游完全相同；代理不加重也不缓解（已接受风险） |
| config.json 内容进索引 | 密钥边界：config 只用于拉起上游进程，任何字段不落 JSONL、不进搜索结果 |
| 调用结果截断 | 透传原则：上游返回什么是上游的事（D-06） |
| 鉴权/授权 | v1 定位本地单用户 stdio 进程 |
| 多工具批量调用 | 一次只调一个，接口极简 |
| 代理自身 HTTP 服务形态 | v1 只 stdio；团队共享实例场景留给 v2（D-16） |

## 关键约束（平台 / 环境 / 技术前提）

| 约束 | 内容 | 对设计的硬影响 |
|---|---|---|
| 平台 | 开发机 Windows（cmd.exe）；部署目标为公司内网主机 | 路径、编码、系统代理坑按 Windows 实测处理；全部文件 IO 显式 UTF-8 |
| 运行时 | Python 3.11+ + uv；纯 Python 零二进制依赖（黄金律 5） | 不引 rg 等外部可执行文件（D-12） |
| 协议 | 官方 `mcp` SDK 2.x，钉 2.3.0，v2 API 词汇（`MCPServer` / `Client` / `httpx2`） | 上游三传输 stdio / Streamable HTTP / SSE（D-08）；SDK 升级须重跑开工首验 |
| 下游形态 | v1 仅 stdio、单客户端；首个宿主为 LangChain DeepAgents 经 langchain-mcp-adapters 挂载 | 不做鉴权/多客户端并发/代理 HTTP 形态（D-16） |
| 网络 | 公司内网不通 GitHub、通 PyPI（或镜像源）；开发留在 GitHub | 分发走 PyPI 公共包（D-19），源码不依赖内网可达 |
| 保密 | config 只用于拉起上游进程，任何字段不落 JSONL、不进搜索响应 | 密钥边界；索引里没有 config 内容 |
| 依赖怪癖 | 下游宿主的 env 白名单可能不含 `NO_PROXY`；Windows 系统代理会劫持 loopback | loopback 上游 `trust_env=False`（D-24） |

## 术语速查（术语——一句话人话）

| 术语 | 人话 |
|---|---|
| JSONL | 一个文本文件，每行一个独立的 JSON 对象 |
| stdio | 用"标准输入/输出"当通信管道——父进程 spawn 子进程，双方按行读写 |
| streamable HTTP | MCP 的一种联网传输方式：走 HTTP 请求而非本地管道 |
| fail-fast / fail-soft | 出错立刻大声退出 / 出错先忍下、跳过继续跑 |
| target | 工具的全名 `服务__工具`，从搜索结果原样复制即可调用 |
| wheel / sdist | Python 的二进制安装包 / 源码安装包 |
| trusted publishing | 用 GitHub Actions 的身份直接签名发布到 PyPI，不长期保存密码令牌 |
| fixture | 测试用的固定环境/道具（本项目的"假上游"就是 fixture） |
| 地基批 / 功能批 | 打测试与度量地基的批次 / 直接交付功能的批次 |
| reasoning_effort | 让推理模型"想多深"的档位参数，low 表示快而省 |
| pp（百分点） | 百分比之间的差，如 82% 与 75% 差 7 个百分点 |
| A/B 双臂 | 同一批任务跑两个对照组（挂代理 vs 直挂上游）再比较 |
| 消融实验 | 把某个设计（如 description 注入）单独关掉再跑，看它到底有没有用 |
